Release Channels

This page is the specification for a release manager / updater / launcher / settings menu for Limey V1 (a Vencord fork). It catalogues every channel name in the release-management space — which ones actually exist in the codebase, which ones are Discord’s own client branches, and which ones are proposed custom labels you can adopt without pretending upstream ships them.

🏷 Origin tiers

Each entry is tagged Official · Limey, Official · upstream Vencord, Discord client, Discord rollout process, or Proposed. Nothing is claimed official unless the code shows it.

📐 Three axes

Names only become useful when split into three orthogonal axes: Track (what code), Host (which Discord build), Rollout (how it reaches users). See the recommended hierarchy.

🔤 Naming

IDs are lowercase kebab-case (stable, dev, canary-rollout), suited for config keys, CLI flags and update feeds. Display names are Title Case for UI menus.

Accuracy notes (read first)

Section titled “Accuracy notes (read first)”
  • What Limey V1 officially ships today. Two build tracks: the Stable builds served by the installer from the Limey backend, and DevBuilds built from source (self-identified, git-based updater active). Both target the desktop Discord app; a Web flavor ships as browser extension / userscript / browser bundle.
  • What upstream Vencord officially ships. The same two-track model (Stable + Development/DevBuild) with web/user builds — Limey V1 inherits it.
  • What Discord ships. Four official client branches: Stable, PTB, Canary, Development (all four are detected by the installer on Linux). Discord additionally runs its own rollout processes (canary rollout, staged/progressive numlock rollouts) — those are processes, not user-selectable channels.
  • Everything else — Preview, Beta, Alpha, RC, Nightly, Snapshot, Edge, Insider, Early Access, LTS, Legacy, hotfix pipelines, blue-green, shadow releases, feature-flagged and A/B testing — is a proposed custom label borrowed from industry practice (GitHub, Chrome, Firefox, Kubernetes, and so on). Adopt them freely; just don’t advertise them as built-in.

Where this spec is implemented

Section titled “Where this spec is implemented”

The registry is not just prose — the platform now serves and renders it:

Integration What it does
GET /v1/channels Schema-versioned manifest (limey.v1/channels/1) of every channel above, each entry carrying origin, stability, cadence and an implemented flag. Single-channel lookup at /v1/channels/:id.
GET /v1/install/files Channel-aware file serving: /v1/install/files/<name> is stable; /v1/install/files/{lts,rc,beta}/<name> serve the frozen snapshots in dist/<channel>/, frozen with pnpm publishChannel <channel>. LTS falls back to the current stable files with the same hash-stamping and HMAC signatures until pinned; RC and Beta answer 503 “not published yet” instead — a pre-release must never be silently replaced by a stable build.
GET /v1/install/desktop The install-info endpoint embeds a channels object: the current track (stable), the docs URL, ltsAvailable, and the four implemented desktop host channels as installTargets, each already mapped to the installer’s --branch value.
Download page (/download) A Release channels section documents the shipped tracks — Stable, Development and the Stable LTS card (with its --channel lts command and live pin status) — and a host picker turns any Discord branch (Stable, PTB, Canary, Development) into the matching installer command. It reads /v1/channels live to confirm the page’s implemented channels match the backend.
Installer --branch / --channel The CLI installer accepts [auto|stable|ptb|canary|development] for --branch — the same ids as the host channels minus the discord- prefix — and [stable|lts|rc|beta|canary|alpha] for --channel (the implemented installable channel subset; preview is a UI label, not an artifact stream). After patching it writes a channel.txt marker into the files dir.
pnpm publishChannel The freeze step: scripts/publishChannel.mjs copies the current desktop build into dist/<channel>/ (requires --force to replace an existing snapshot). LTS is effectively a permanent pin; RC is re-frozen once per release cycle, Beta per feature batch, and both land in stable when clean.
Updater channel persistence The desktop updater reads that marker and keeps updating within the installed channel: LTS/RC/Beta installs fetch /v1/install/files/<channel>/* and that channel’s hash, so they never silently migrate back to stable.
Bot SDK client.channels list(), get(id), manifest(), plus implemented(), byCategory() and installTargets() (implemented desktop hosts with their --branch values) for bots and tooling that want to report or validate channels.
Updater settings section The desktop settings Updater tab shows the active track (stable or dev via the standalone-build rule) and names the planned channels explicitly as not shipping yet.
Updater runtime Builds are tagged at compile time: --standalone → stable, source builds → dev (DevBuild self-identification, git updater).

Proposed channels stay definition-only everywhere: no artifact paths, feed URLs or branches exist for them, here or in the API.

Stability scale

Section titled “Stability scale”

All rows below use this five-level scale:

Level Meaning
Production Fit for default use by anyone; releases are deliberate and reviewable
Testing Reasonably safe; expect occasional rough edges
Unstable Minutes-to-hours freshness; breakage is expected, not exceptional
Volatile Arbitrary machine state; no support contract
Internal Diagnostic-only; never distribute

1. Main release channels

Section titled “1. Main release channels”

Sorted most stable → most experimental.

ID Display Name Origin Description Intended audience Stability Update frequency Recommended use case
stable Stable Limey / Vencord / Discord The default, reviewed track. Installer pulls hash-stamped builds from the Limey backend; changelog is cut per release. Everyone Production Deliberate (per feature batch or fix) Daily use; the only track recommended to non-developers
lts Stable LTS Limey A frozen snapshot of stable supported for a long window, accepting only security and crash fixes. The backend freezes a copy of the stable build into dist/lts/; until that first pin is published, --channel lts installs track the current stable build, and the in-app updater keeps updating within the channel either way. Hosters, admins, people who hate change Production Rarely → never Downtime-sensitive setups, fork packagers
rc Release Candidate Limey (concept: upstream RC flows) The final pre-release of the next stable version; feature-complete, only crash/security fixes allowed. Folded into stable once clean. The build is frozen into dist/rc/ per release cycle (pnpm publishChannel rc); while no snapshot is published the channel answers “not published” rather than silently serving stable, which is older. Testers and plugin authors pre-validating Testing One per release cycle Verify “breaking” changes before they reach everyone
beta Beta Limey (concept: upstream Vencord plugin-level beta exists via plugin beta field, but not as a client channel) Public pre-release track accumulating features for the next version; wider audience than RC, less polish. Published to dist/beta/ per feature batch like RC, same not-published semantics between batches. Curious users who accept some breakage Testing Per feature batch Trying features early without maintenance-every-day cost
ptb Public Test Build (PTB) Discord Discord’s own public-testing client branch. Limey V1 installs into it (installer detects DiscordPTB), but PTB itself is Discord’s release cadence, not a Limey channel. Discord testers Testing (Discord’s choice) Discord-driven, weekly-ish Reproducing Discord-platform bugs; early Discord features
preview Preview Proposed (label concept) Neutral umbrella “pre-stable” name for people who want newer-than-stable but not bleeding-edge. Implemented as a UI alias for the pre-release family (rc/beta) — it resolves to those channels and has no build stream of its own. Non-technical early adopters Testing With each dev batch A friendly label for an “opt into newer stuff” toggle in settings UI
canary Canary (Limey) Limey The freshest shipped pre-release of the next version, refrozen per batch ahead of Beta (pnpm publishChannel canary, unpublished batches answer “not published”). The docs deliberately keep the Discord Canary branch under the discord-canary host channel and the gradual delivery under canary-rollout — Limey’s canary is a build stream, not either of those. Adventurous testers Unstable Per batch Newest next-version content without leaving the updater’s channel stream
alpha Alpha Limey (concept: pre-release alpha flows) The earliest shipped pre-release: code that will change shape, frozen per fresh feature batch before it reaches canary/beta, accepting breakage by design (pnpm publishChannel alpha). Plugin developers porting against the upcoming internal API Unstable Per batch, before beta Porting plugins to upcoming internal API changes

Overlap notes. beta/rc/preview describe stages of the same flow (feature-batch → polish → freeze). Keep all three only if you want a public changelog narrative; otherwise collapse to preview.

2. Development channels

Section titled “2. Development channels”

Sorted most usable → most volatile.

ID Display Name Origin Description Intended audience Stability Update frequency Recommended use case
dev Development Limey / Vencord (official; the “DevBuild”) Source-built flavor of Limey V1. Self-identifies as a DevBuild (support warning + git updater active) instead of silently pretending to be a release. Developers, contributors, power users Unstable Per commit; git updater pulls from the repo Debugging, contributing, running new plugins before they’re blessed
devbuild DevBuild Limey / Vencord (official alias) The runtime label of a dev build. Use as an alias in the updater so “Am I on devbuild?” logic has one canonical id. (same as dev) Unstable = dev Same as dev; keep as alias, not separate channel
source Source Build Limey / Vencord (officially supported) Any install built by the user from their own checkout (e.g. the local dev scripts). Includes locally modified code; updater operates against git by definition. Developers Volatile On next manual build Verifying fixes before contributing; hot-patching upstream
custom Custom Build Proposed (extends the above) A user-built flavor from a fork with extra patches, distinct branding or plugin changes. Needs a channel-owner field so the updater knows who’s authoritative. Fork maintainers Volatile Owner-driven Community forks, personal modpacks of plugins
nightly Nightly Proposed (Firefox-model name) Scheduled (e.g. 00:00 UTC) snapshot of the main branch, built automatically even if commits are broken. Continuous-testers & plugin CI Unstable Daily Automated cross-testing; making “I update once a day” a promise
snapshot Snapshot Proposed Point-in-time named dev build (like Gradle/JVM snapshots). Differentiator vs nightly: snapshot inclusion is manual or gated by tests, nightly is a cron. Same as nightly Unstable Irregular Publishing “here’s a build with the fix to test” quickly
edge Edge Proposed (Heroku/Vercel-model name) Purest freshness: same-source as nightly but built per successful push, no schedule. CI systems, ultra-impatient contributors Volatile Per push Smoke-testing the exact commit that just landed
experimental Experimental Proposed Aggregates exceptional, opt-in functionality(feature-flagged plugins, rewrites) pinned to a stable-ish base.
Plugin authors & opt-in flag flips Unstable / Volatile With the experiments Testing one specific feature without taking all dev-build risk
debug Debug Proposed Builds with verbose logging, sourcemaps, devtools unwrapping, integrity checks off — never meant to leave a machine. Support for reports: “please attach a debug-build log”. Core developers Internal On demand Diagnosing silent failures in stable or dev

Overlap notes. nightly vs snapshot vs edge differ only in what triggers a build (cron / test-gate / push). Ship one of them; pick nightly if you want a Firefox-style cadence, edge if you want maximum freshness. dev vs devbuild: keep dev as the channel id and devbuild as its display/runtime alias so existing error-report wording keeps working.

3. Early access channels

Section titled “3. Early access channels”

All of these are Proposed — none exist anywhere upstream. They exist to give marketing-friendly names to subsets of the technical channels above.

ID Display Name Origin Description Intended audience Stability Update frequency Recommended use case
early Early Access Proposed Paid/logged-in users get the next feature batch a little earlier, still built from rc-quality code. Limes perk-tier subscribers (optional perk on the economy tiers) Testing Same as beta/rc An “offline-friendly opt-in” in the settings menu
insider Insider Proposed (Windows/Chrome-model name) A “read the dev diary” crowd — same artifacts as beta but with release notes aggregated per batch rather than per channel. People who want to know why changes are happening Testing Batch-shaped Same artifact as beta; choose purely for naming/UX preference
preview-ch Preview Channel Proposed (Android/model name) Just a friendlier display name for beta. Kept here so the settings menu can say “Preview (Beta)” without looking jargonny. Same as beta Testing Same as beta Pure naming-fallback; another name users search for
dev-preview Developer Preview Proposed Guaranteed spec-stable-ish subset of the upcoming release — the ones plugin authors depend on (API changes, plugin manifest schema, patch points). Plugin ecosystem maintainers Testing (API-frozen) Per planned release milestone Migrating to the next plugin API before it ships
internal Internal Testing Proposed Small ring for core collaborators before anything public: internal checksums, unreleased ban-heuristic tuning, security-sensitive fixes. Core team Testing or worse Irregular Round-0 verification of an upcoming security patch
community Community Preview Proposed Public “vote on what’s next” lobe where the top-voted candidate experiments advance to beta. Plugin community, store authors Testing Community-driven Democratic direction-setting, not just bug-catch

Overlap notes. early / insider / preview-ch are branding names for more or less the same artifact as beta — pick one word for your UI and define the rest as aliases in the release-manager data model rather than shipping three independent channels.

4. Deployment / rollout strategies

Section titled “4. Deployment / rollout strategies”

These are Discord·process (where they exist at Discord) or Proposed/proven industry patterns — strategies, not user-selectable channels. A release manager should pair each with one or more tracks from the tables above.

ID Display Name Origin Description Intended audience Stability Update frequency Recommended use case
full Immediate / Full rollout Concept everywhere, effectively what Limey V1 does today Newest build is served to everyone as soon as its hash changes. Everyone Production Per release The default, matches current Stable
canary-rollout Canary Rollout Discord·process / Proposed for Limey V1 Ship first to a tiny percentage of volunteers (often dev-track users) before the broader audience. Volunteers Production (early cohort) Per release, percentage-driven Catch client-specific regressions with minimal blast radius
progressive Progressive Rollout (Staged rollout) Discord·process (numlock-based % cohorts are in Discord’s own updater) / Proposed Percentage cohorts (1% → 10% → 50% → 100%), each gated on error telemetry. Everyone, spread over time Production Per release window Universal, boring, extremely effective default
phased Phased Rollout Proposed (same family, cohort-by-cohort on a calendar rather than telemetry) Fixed dates for steps (“2026-10-25: 10%”) rather than percentage health gates. Ops/forks with uptime contracts Production Planned windows Coordinating across maintainers, companies or server regions
rolling Rolling Release Proposed (apt/arch/Rust toolchain model name) No versioned releases at all — updates continuously. Developers & tinkerers Unstable Continuous Exactly what dev already is; use this term when explaining the model, not as a channel
bluegreen Blue-Green Deployment Proposed (deployment topology, not a channel) Run current build (blue) and new build (green) simultaneously; switch the pointer after health-check. Backend / server.js wearing hats Production Per deploy Zero-downtime backend deploys for the Limey V1 API itself
shadow Shadow Release Proposed New code runs, takes traffic, produces logs/metrics, but its user-visible output is discarded. Performance & safety instrumentation Internal Per experiment Measuring a rewritten patching routine against identical Discord traffic
featureflagged Feature-Flagged Release Proposed (well-established industry pattern) Ship a binary to stable containing disabled features, then enable them per-user remotely. Everyone (features are opt-in, code path is shared) Production Continuous, no re-install needed Frequent-Safe experimentation without new builds; pairs perfectly with Limey’s Limes/perk tiers to gate early access
abtest A/B Testing Proposed (established industry pattern) Two variants of the same feature delivered to random cohorts, decision made on measured outcomes. Data-driven UI/UX work Production (per-cohort) Per experiment Reflowing plugin-store pages or settings-menu UX with real data

Overlap notes. canary-rollout ⊂ progressive ⊂ phased — the same family at different calibration styles (volunteer / telemetry / calendar). Pick exactly one as the Limey V1 production strategy; keep the others in the release-manager schema as synonyms for different sensitivities.

5. Maintenance and support channels

Section titled “5. Maintenance and support channels”

States and processes a track can enter — not (usually) channels users choose.

ID Display Name Origin Description Intended audience Stability Update frequency Recommended use case
lts Stable LTS Proposed See §1. A state stable may enter: a release line is declared LTS and stops taking features. Long-cycle operators, maintainers, packagers Production Security/crash-fixes only for the frozen window Long-supported install baselines
maintenance Maintenance Release Proposed Bug-fix-only drop on an otherwise-frozen track. Users of a given version Production As bugs are fixed Polish between feature batches
hotfix Hotfix Proposed (standard industry idiom) Out-of-band patch applied bypassing normal gates because the live product is broken. Everyone (fast-tracked) Production (usually) As needed Fixing a broken build or a widespread plugin outage right now
security-patch Security Patch Proposed (concept known industry-wide; upstream Vencord itself does push urgent fixes) Same as hotfix, plus silent deploy priority — security-sensitive fixes should reach stable before a changelog is cut. Everyone Production As vulnerabilities are found Patching patchers or anti-scam/anti-scam heuristics
rollback Rollback Proposed (operations concept) Re-point users to the previous hash after a bad release. Keeps a “last known good” pointer in the backend to enable one-click revert. Users being protected Production Emergency only Recovering from a bad stable push without waiting for the next patch
legacy Legacy Proposed Old client-version-limited builds kept around for users who cannot (or will not) update their Discord client. Tool must state concrete “supported until” dates. Users on old Discord versions Testing (frozen) Patch-stratified, rare Long-tail Discord-version support
deprecated Deprecated Proposed (real concept upstream for plugins, proposed here for tracks) A channel scheduled to be removed; updater should nag with a transition link. Everyone Any Until removal Cleaning up rarely-loaded channels without surprise delivery
archived Archived Proposed Read-only snapshots of any channel, no binaries served, no support. Users cannot “install” it; they can only inspect old artifacts. Historians, forensics Frozen Never updates Audit trail, crash-regression archaeology

Overlap notes. hotfix / security-patch / maintenance are the same mechanism at different urgencies (breakage → fix, vulnerability → fix, minor bug → fix). Keep IDs distinct in the schema so a release manager can attach different deploy gating to each, even though they reuse the same artifact pipeline. legacy/archived/deprecated/lts are all states a track can be in, with distinct user promises (old-but-hot / read-only / dying / long-supported).

6. Discord client compatibility (install targets)

Section titled “6. Discord client compatibility (install targets)”

These are Discord’s own client branches plus where Limey V1 actually runs. The installer already detects and supports all four desktop branches, and the web bundle runs in browsers. Keep these as a second axis in your release manager (host), never as a replacement for the first (track).

ID Display Name Origin Description Intended audience Stability Update frequency Recommended use case
discord-stable Discord Stable Discord The mainstream Discord desktop app everyone has. Everyone Production (Discord’s) Weekly-ish, Discord-driven Default install target
discord-ptb Public Test Build (Discord PTB) Discord Discord’s wide pre-stable branch, available on the Download page. Opt-in testers Testing (Discord’s) Weekly-ish, before wide release Bug replication; early CSS/DOM drift
discord-canary Discord Canary Discord Discord’s fastest-moving client, near-day freshness. Discord-adjacent testers Unstable (Discord’s) Near daily Catching patch targets the moment they drift
discord-development Development (Discord Development) Discord Discord’s internal-flavor branch occasionally distributed for testers. Discord staff & client mod devs Volatile (Discord’s) Erratic Verifying patches against unreleased internal BFS
desktop Desktop Client (patched Discord app) Limey / Vencord Limey V1’s format: injected patcher.js/preload.js/renderer.js/renderer.css installed into one of the four Discord branches above by the installer. Desktop users Depends on the track chosen Per station’s track The main product on the desktop
web Web Client (browser) Limey / Vencord Limey V1’s browser bundle — Chrome MV3 extension, Firefox MV2 shell, userscripts for discord.com. Browser-first users (incl. mobile Discord web) Matches stable (web usually ships stable-only) Per stable release Users who can’t or won’t run an injector/UI installer
custom-client Custom Client Build Proposed Any other Discord-compatible client (VDI, EmbeddedApp builds, Electron-based forks shipped by other projects). Disclaimer required: compatibility is not guaranteed, plugin authors can’t test against it. Fork operators Volatile Owner-driven Power users in restricted environments

Overlap notes. discord-canary (a Discord client branch) is often confused with “Limey V1 canary” (a track of Limey V1 code). In a release manager they should be two different fields — e.g. track: canary-rollout plus host: discord-canary — even though the installer just reads the code for whatever Discord branch it sits inside.

Concrete recommendations for the Limey V1 updater

Section titled “Concrete recommendations for the Limey V1 updater”
  1. Ship today’s reality under two IDs. Keep stable and dev as the only two selectable tracks in the settings dropdown for the MVP, with devbuild as dev’s display alias. Everything above is additive.
  2. Model channels as data, not code. A channel is an object — { id, displayName, description, audience, stability, cadence, origin, supportedHosts, artifacts, rollout } — so the same spec powers the settings dropdown, the CLI (--track dev --host discord-ptb), and the changelog page.
  3. Never let rollout override track. % cohorts and hotfix-priority apply within a track; they are not new tracks. This is what keeps “why am I not on the newest version?” support tickets answerable.
  4. Aliases, not duplicates. preview-ch→beta, insider→beta, snapshot→nightly, rolling→dev, security-patch→hotfix (with a flag) — collapse the naming family onto one canonical artifact.
  5. Mark proposed names visually. In the settings UI, render unimplemented channels as grayed-out with a “coming later” tooltip so users never believe a non-existent feed exists.
